# ADR-0020 — Useful-output pipelines: демо как поверка с чатом, консолидация воркеров, wake-on-HTTP

- **Status:** Accepted (2026-06-10)
- **Date:** 2026-06-10
- **Deciders:** Alex, Claude
- **Supersedes:** — (расширяет ADR-0008; уточняет позицию «demo agents deliberately trivial» из `docs/what-sage-is-and-isnt.md`)
- **Related:** ADR-0007 (observable decomposition), ADR-0017/0019 (arbitration + council), ADR-0018 (content envelope), M11 «useful outputs» (TASKS.md)

## Context

Демо-режимы v2 (pipeline / sentiment / vision) доказывают протокол, но не дают пользователю ничего, что он унесёт. Поверка, по которой нас будут судить, очевидна: один и тот же промпт в ChatGPT, Claude и Sage. В лобовом сравнении «чей артефакт лучше» мы проигрываем — у чата фронтирная модель и ноль orchestration-оверхеда. Но у чата есть три структурные слабости, которые пользователи знают на своей шкуре: (1) **нет финишной черты** — один index.html и бесконечный цикл правок; (2) **протухшая память** — цитирует внутренние знания вместо реального поиска, цитаты не резолвятся; (3) **vibes вместо находок** — ревью без структуры, ответственности и следа. Sage-пайплайн с definition of done, принудительной верификацией и деньгами, которые движутся только после проверки, бьёт ровно в эти три точки.

Параллельно — операционное ограничение: текущая модель «один агент = один Fly-процесс (+standby)» упирается в лимит машин организации (см. [[gotcha-fly-org-machine-limit]]) и не масштабируется на 8–10 новых capabilities.

## Decision

1. **Три композитных пайплайна с полезным выводом**, в порядке от простого к сложному:
   - **Website** — «сайт-визитка»: copywriter → builder → packager. Артефакт = **zip с проектом, готовым к деплою + README-инструкции**; QA-гейт (HTML-валидация, Lighthouse, скриншот-превью в UI). Live-deploy на поддомен — опциональная фаза 2 (policy-check-шаг + авто-экспайр продуманы, отложены).
   - **Research-репорт с fact-check'ом** — searcher (реальный SERP) → extractor → synthesizer → **fact-checker (платный evaluator)**: цитаты обязаны резолвиться; отклонение → dispute → council (M11.4). Флагман нарратива поверки; включает управляемый сценарий «покажи неудачный ран».
   - **Structured review** — разбивка по модулям → findings (file:line + severity + воспроизведение) → **независимый второй ревьюер (другая модель)**, расхождения видимы → EAS-аттестация хэша отчёта. Framing строго «structured review, educational — not a security audit».
2. **Demo-нарратив = «три боли чата»**: бесконечная правка / протухшая память / vibes вместо находок. Протагонист UI — lifecycle (plan card, цены, escrow-статусы, tx), артефакт — второй план. Сравнение с чатом проводим сами, на своих условиях, включая показ провала (деньги не ушли).
3. **Agent identity ≠ процесс.** Identity = кошелёк + запись в AgentRegistryV2. Хостинг — консолидированные generic-worker процессы на Fly, каждый держит несколько identities/capabilities. Orchestrator + 1–2 worker-процесса вместо 1-процесс-на-агента.
4. **Wake-on-HTTP вместо постоянного watch.** Orchestrator после `createTask` пингует endpoint воркера; Fly auto_start поднимает машину; воркер на boot сверяет on-chain состояние (закрывает и потерянные события), исполняет, auto_stop. Scale-to-zero по умолчанию. Reference-агенты остаются portable Node + Docker — та же модель, что мы предлагаем foreign-агентам (`templates/foreign-agent/`).
5. **Evaluator — унифицированная платная роль** каркаса (fact-checker, QA, второй ревьюер — инстансы одной роли), мост к арбитражу M11.
6. **Снос старых воркеров** (translator, sentiment, vision) и их demo-режимов — **финальным шагом**, после того как первый новый пайплайн прошёл e2e на Base mainnet (pipeline-режим до этого остаётся регрессионным базисом). Summarizer выживает как capability внутри research.
7. **Гарды ADR-0007 обязательны до первого публичного рана:** budget cap на parent task, max-depth, circuit breaker.

## Rationale

- Поверка с чатом неизбежна; выигрышная дисциплина — не качество генерации, а финишная черта + принудительная верификация + видимая судьба денег при провале. Провал не показывает никто из конкурентов.
- Research-пайплайн — единственное место, где у нас прямое **качественное** преимущество (резолвящиеся цитаты против галлюцинаций чата), поэтому он флагман нарратива, хотя website проще и идёт первым в реализации.
- Архив вместо live-deploy убирает модерацию публичного контента, hosting lifetime и deploy-credentials — три внешних узла — при сохранении вау-эффекта через скриншот-превью.
- Консолидация identity/процесс решает лимит машин архитектурно, а не сносом; wake-on-HTTP делает воркеров почти stateless и переносимыми.
- «Useful outputs» уже зафиксирован как столб M11 — этот ADR доводит его до требования к демо, не отменяя «воркеры = reference implementation».

## Alternatives considered

### A. Оставить демо тривиальным (позиция what-sage-is-and-isnt as-is)
- Pros: чистота категории «мы settlement, не агенты»; ноль новых costs.
- Cons: поверка с чатом проигрывается всухую; пользователь не уносит ничего; M11-столб «useful outputs» повисает.
- Отвергнуто: категорию можно держать копирайтом, а не бесполезностью вывода.

### B. Live-deploy сайта сразу (v1)
- Pros: максимальный вау («вот URL»).
- Cons: модерация чужого контента, credentials, lifetime, abuse-вектор — до первого публичного рана.
- Отвергнуто для v1: архив даёт 80% эффекта без внешних рисков; live-deploy — фаза 2.

### C. Cloudflare Workers/DO для агентов
- Pros: стек уже на CF; нет cold-start машин.
- Cons: минутные LLM-пайплайны плохо ложатся на request-driven модель; ломает симметрию с foreign-agent template (fork-and-run Node+Docker).
- Отвергнуто: reference-агенты должны хоститься так же, как мы предлагаем операторам.

### D. VPS (Hetzner)
- Pros: дешевле, без лимитов машин.
- Cons: минус autoscale, новая ops-поверхность, миграция с готовых ранбуков/secrets.
- Отвергнуто сейчас; запасной вариант.

### E. Один агент решает композитную задачу соло (без найма)
- Pros: проще, быстрее.
- Cons: исчезает agent-hires-agent, per-step settlement становится чистым театром; не демонстрирует протокол.
- Отвергнуто: терялся бы смысл демо.

## Consequences

**Positive:** поверка с чатом становится выигрываемой и проводится на наших условиях; артефакты, которые пользователь уносит (zip, репорт с цитатами, подписанный review); evaluator-роль связывает пайплайны с арбитражем M11; ресурсы Fly под контролем архитектурно; материал для grant-заявок (Circle/Base) — живые tx на каждом шаге полезной работы.

**Negative / trade-offs:** стоимость рана растёт (research: SERP API + больше токенов) — бюджет на ран и цены шагов считать до публикации; сложность каркаса (generic worker, wake-on-HTTP) — новый код до первого видимого результата; сдвиг задокументированной позиции требует синхронного обновления `what-sage-is-and-isnt.md`; review-пайплайн — репутационный риск при небрежном framing'е.

**Risks:** wake-on-HTTP — потерянный пинг = зависшая задача → boot-reconciliation + escrow-reclaim (CR.3) как страховка; «провальный ран» в демо может быть прочитан как нестабильность → копирайт должен явно маркировать его как фичу; чат-продукты отращивают agent-mode → website-преимущество временное, долгосрочный слой — верификация + settlement (фиксируем это ожидание здесь).

## Amendment 2026-06-12 — hosted preview (одобрено Alex)

Пункт 1 откладывал live-deploy в фазу 2 (модерация, lifetime, credentials). Принята облегчённая форма: **hosted-превью** `GET /preview/:sha256/*` на gateway — отдаёт файлы QA-прошедшего сайта из R2-манифеста. Содержание рисков: hash-URL (не vanity), TTL артефакта (30 дней), `X-Robots-Tag: noindex`, CSP `sandbox allow-scripts` (без cookies/storage на origin gateway), существует только для контента, прошедшего пайплайн (QA-судья видел рендер). Полный live-deploy на поддомен с credentials остаётся фазой 2. Контекст: M12.1.7, фидбек «нечего показать без скачивания и распаковки».
